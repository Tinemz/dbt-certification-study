# Onboarding

Four steps, in order. Each one feeds the next — do not skip ahead to the plan.

If `plan.yml` already exists, say what it currently holds (exam date, hours per week, phase count)
and confirm the user wants to rebuild before overwriting it.

## 1. Level

One `AskUserQuestion` call carrying three questions:

1. **Hands-on dbt experience** — `never used it` · `under 6 months` · `6 months to 2 years` ·
   `2+ years`.
2. **What you have actually shipped** (multi-select) — incremental models and snapshots ·
   contracts, versions and constraints · tests, including unit tests · state, deferral and Slim CI ·
   exposures and source freshness · Python models, packages and macros.
3. **dbt Core or dbt Cloud day to day** — `Core (CLI)` · `Cloud` · `both`.

Why question 3 matters: the exam targets **dbt Core 1.11**. Someone who only works in Cloud
usually has gaps in CLI flags, `--state` plumbing and `dbt retry`, even with years of experience.
Weight those topics up.

The official guide recommends SQL proficiency plus 6+ months of hands-on dbt. If the answer to
question 1 is `never used it`, say plainly that the certification assumes production experience
and that a plan can only partly substitute for it. Then continue — it is their call, not yours.

## 2. Time budget

A second `AskUserQuestion` call:

1. **Exam date** — `already booked` · `booking within a month` · `no date yet`.
   If booked, ask for the date in the next message and accept `YYYY-MM-DD` or plain text.
2. **Hours per week** — `up to 3` · `4 to 7` · `8 to 14` · `15+`.

With a date, the plan is measured in days until it. Without one, the plan is measured in weeks
sized by the weekly hours.

Sanity-check the combination out loud before moving on:

| Situation | What to say |
|---|---|
| < 7 days, or < 4 h/week with a date under 3 weeks away | The plan will cover the heaviest topics only. Coverage will be partial — say so, and suggest moving the date if it is still movable. |
| No experience + under 4 h/week | Realistic preparation is months, not weeks. Offer a plan without a target date. |

## 3. Diagnostic

Run the `diagnostic` mode of the `mock-exam` skill. Two sizes — offer both, recommend the first:

- **full** — one question per sub-skill, 31 questions, roughly 40 minutes. The plan that comes out
  of it is per-sub-skill.
- **short** — one question per topic, 7 questions. Faster, but the plan can only be ordered by
  topic, and sub-skill priorities inside a topic will be guesses. Say that when offering it.

Everything else follows `mock-exam`: never reveal answers mid-exam, capture confidence on every
question, grade at the end, write `exams/attempts/YYYY-MM-DD-diagnostic.yml` and update
`progress.yml`.

Expect a low score and say so upfront. The diagnostic locates gaps; it does not measure readiness.

## 4. Write the plan

Produce `plan.yml` first, then `STUDY-PLAN.md` from it.

### Ordering rules

1. **Adjusted accuracy decides the order.** Discount every `chute + correct` answer before ranking
   — a lucky guess is not knowledge. Worst-adjusted topic goes first.
2. **Misconceptions outrank everything.** Any sub-skill answered `alta + wrong` goes into phase 1,
   whatever its topic's ranking. Nothing signals the candidate to check a confident wrong belief.
3. **Break ties by exam weight.** A topic's weight is its sub-skill count in `exam/topics.yml` —
   topic 01 is 14 of 31 and can never be left to the last day.
4. **Let declared experience adjust, not override.** An area never shipped in production moves up;
   an area shipped for years *and* clean in the diagnostic moves down. The diagnostic wins on
   conflicts — it is evidence, the questionnaire is self-report.
5. **Reserve the last 15–20% of the time** for a full 65-question mock plus review. No new material
   on the final day.
6. **Group interlocking sub-skills into one phase.** `--state`, deferral, Slim CI, `dbt clone` and
   `dbt retry` are one subject, not five.
7. **Anchor each phase to a checkpoint** in `exam/learning-path.md`, so the user knows which
   official courses and docs pages belong to it.

### `plan.yml`

```yaml
# Generated by the onboarding skill. Re-run /onboarding to rebuild it.
created: 2026-09-17
start_date: 2026-09-17
exam_date: 2026-10-30       # null when no date is set
hours_per_week: 8
experience:
  level: 6mo-2y             # none | under-6mo | 6mo-2y | 2y-plus
  platform: core            # core | cloud | both
  shipped: [incremental, tests]
phases:
  - days: [1, 3]            # day numbers from start_date; weeks when there is no exam date
    title: Topics 07 and 02
    why: Weakest at diagnostic; 5 sub-skills between them
    topics: ["07", "02"]
```

Rules for the file: phases are contiguous and cover every day from 1 to the last; `topics` holds
topic ids from `exam/topics.yml` and is empty for mock/review phases; `why` is one line, no prose.

### `STUDY-PLAN.md`

Rewrite it completely — the version in the repo is an example from someone else's run. Keep it to
four sections:

1. **Header** — target date (or "no date set"), hours per week, and one line on how the order was
   derived.
2. **Next session: start here** — run `status.py`, study what it names, re-test with a `weak` drill.
3. **The sequence** — one block per phase: days, topics, what to cover, the learning-path
   checkpoint it maps to.
4. **Rules that keep this honest** — declare confidence truthfully, record every drill, and a
   passing practice score is not readiness (practice questions are original and uncalibrated;
   treat anything under 80% on a full mock as not ready).

Never write live scores into `STUDY-PLAN.md` — `status.py` derives those from `progress.yml`.

## Close

Print the plan's shape in three lines: number of phases, what phase 1 is, and the date of the first
full mock. Then point at `.venv/bin/python3 status.py` as the entry point for every session after
this one.

Do not commit unless the user asks. If they do, the commit message is in PT-BR.
